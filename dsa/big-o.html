Big-O: how your code scales

Big-O answers one question: when the input gets 10× bigger, how much more work does my code do? Every Google interviewer will ask you for it after you code, so it's the first thing to master.

The idea

It measures growth, not speed

Big-O ignores your laptop, your language, and small constant costs. It only describes the shape of the work as the input size n grows.

Real-life example: you need to find your friend Priya in a building.

  • If you know her room number, you walk straight there. It takes the same time whether the building has 10 rooms or 10,000. That's O(1).
  • If you knock on every door until you find her, a building with 10× the rooms takes about 10× the time. That's O(n).
  • If, for every room, you also check every other room to compare notes, 10× the rooms means 100× the work. That's O(n²).
Big-O usually describes the worst case: Priya is in the last room you check. Interviewers expect worst case unless you say otherwise.

The seven classes

Every complexity you'll meet, fastest to slowest

O(1)Constant

The work doesn't depend on n at all. One step or fifty steps, as long as it's a fixed number.

Real life

Grabbing your coat from a coat check with ticket #47. The attendant goes straight to hook 47, no matter how many coats are stored.

In code 
arr[47]          # index into a list
d["priya"]       # dict lookup (average)
x in my_set      # set membership
stack.append(5)  # push onto a list

Why a dict is O(1): the key is hashed straight to a slot, like the ticket number points to a hook.

O(log n)Logarithmic

Each step throws away half (or some fixed fraction) of what's left. Doubling n adds only one more step. For a million items, that's about 20 steps.

Real life

Guessing a number from 1 to 1,000 when someone says "higher" or "lower." Always guess the middle: 500, 250, 375… You never need more than 10 guesses.

In code 
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target: return mid
        if arr[mid] < target: lo = mid + 1
        else: hi = mid - 1  # half gone
    return -1

Also O(log n): heapq.heappush, lookups in a balanced tree, and any loop like while n > 1: n //= 2.

O(n)Linear

You touch each item a constant number of times. Twice the input, twice the work. Most good interview solutions land here.

Real life

A teacher reading the attendance list out loud. 30 students, 30 names. 300 students, 300 names.

In code 
def find_max(nums):
    best = nums[0]
    for x in nums:      # n steps
        best = max(best, x)
    return best

Two separate loops over the list are still O(n): 2n steps, and constants get dropped.

O(n log n)Linearithmic

The cost of good sorting. You do O(log n) rounds, and each round touches all n items.

Real life

Sorting a stack of exam papers alphabetically by splitting it in half, sorting each half, and merging. Each "level" of merging handles every paper once, and there are about log n levels.

In code 
nums.sort()          # Timsort: O(n log n)
sorted(words)

# common pattern: sort first, then scan
nums.sort()                    # n log n
for i in range(1, len(nums)):  # n
    ...
# total: O(n log n)

Interview signal: if your idea starts with "sort the array," your floor is O(n log n). Ask yourself whether a hashmap could get you to O(n).

O(n²)Quadratic

For every item, you look at every other item. Usually a nested loop. Fine for n in the low thousands, too slow beyond that.

Real life

Everyone at a party shakes hands with everyone else. 10 people make 45 handshakes. 100 people make 4,950. The party doesn't get 10× longer, it gets about 100× longer.

In code 
# brute-force Two Sum
for i in range(n):
    for j in range(i + 1, n):
        if nums[i] + nums[j] == t:
            return [i, j]

The inner loop runs n−1, n−2, … 1 times. That adds up to n(n−1)/2, which is still O(n²). Starting at i + 1 halves the work but doesn't change the class.

O(2ⁿ)Exponential

Each extra item doubles the work. Shows up when every item is a yes/no choice, or when recursion branches twice and recomputes the same things.

Real life

Packing for a trip with 20 items and trying every possible combination of what to bring. Each item is in or out, so that's 2²⁰ ≈ 1 million combinations. Add 10 more items and it's a billion.

In code 
def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)
# 2 branches per call, depth n
# → O(2ⁿ). fib(40) takes ~1 min

Fix: memoization (cache each fib(k)) turns this into O(n). That's the core idea of dynamic programming, which you'll meet in Week 7.

O(n!)Factorial

Trying every possible ordering. Only usable for tiny n (about 10 or less).

Real life

A delivery driver with 12 stops trying every possible route order to find the shortest. That's 479 million routes. With 20 stops, it's more routes than there are grains of sand on Earth.

In code 
from itertools import permutations
for route in permutations(stops):
    check(route)   # n! routes

You'll see this in backtracking problems like Permutations (Week 7), where listing every ordering is the task.

How to analyze any code

Seven rules that cover almost everything

Drop constants

O(2n), O(n + 100), and O(n/2) are all O(n). Big-O is about shape, not exact counts.

Keep only the biggest term

O(n² + n) becomes O(n²). When n is a million, the extra n is a rounding error.

Steps one after another: add

for x in a: ...   # O(n)
for y in a: ...   # O(n)   → O(n + n) = O(n)

Steps inside each other: multiply

for x in a:        # n times
    for y in a: ... # n times each → O(n · n) = O(n²)

Different inputs get different letters

Looping over list a then list b is O(a + b). Nesting them is O(a · b), not O(n²). Interviewers check for this.

Halving means log

Any loop that cuts the problem in half each time (n //= 2, binary search, going down a balanced tree) runs O(log n) times.

Recursion: branchesdepth

A function that calls itself b times and goes d levels deep does about O(bd) calls. fib has 2 branches and depth n, so O(2ⁿ).

Hidden loops count too. x in my_list, my_list.index(x), my_list.insert(0, x), slicing s[a:b], and "".join(...) each take O(n) on their own. A "single" loop that uses one of them is often secretly O(n²).
Worked example

Analyzing a function line by line

Does a list contain two numbers that add up to target? Here are two versions with the same answer and very different costs.

Version A: brute force

for i in range(len(nums)):

Outer loop runs n times.

    for j in range(i+1, len(nums)):

Inner loop runs up to n times for each i. Nested, so multiply.

        if nums[i]+nums[j]==target:

Constant work, O(1).

Time O(n²), space O(1). For 100,000 numbers that's about 5 billion checks, roughly 8 minutes in Python.

Version B: hash set

seen = set()

Extra memory that can grow to n items.

for x in nums:

One pass: n times.

    if target - x in seen: return True

Set lookup is O(1) on average.

    seen.add(x)

Also O(1).

Time O(n), space O(n). Same 100,000 numbers: about 0.01 seconds. You traded memory for speed, which is the single most common trade-off in interviews. Say it out loud when you make it.

Space complexity

Memory follows the same rules

Space complexity counts the extra memory your code uses as n grows, not counting the input itself.

CodeExtra spaceWhy
Two pointers on the input listO(1)A few variables, no matter the size.
seen = set() filled in a loopO(n)Can end up holding every item.
Recursion n levels deepO(n)Each waiting call sits on the call stack. People forget this one.
Recursive binary searchO(log n)The stack is only log n calls deep.
An n × n grid of results (2D DP)O(n²)n² cells stored.

Python's recursion limit is 1,000 by default, so deep recursion can crash on big inputs even when the Big-O looks fine.

Interview trick

Read the constraints to guess the target

LeetCode problems list the maximum input size. Working backwards from roughly 10⁷–10⁸ operations per second tells you which complexity the interviewer is expecting before you write a line.

If n is up toAim forTypical approach
~10O(n!)Try every ordering (permutations)
~20O(2ⁿ)Try every subset, backtracking
~500O(n³)Triple loops, some DP
~5,000O(n²)Nested loops, 2D DP
~10⁵ to 10⁶O(n log n) or O(n)Sorting, heaps, hashmap, two pointers, sliding window
10⁹ or moreO(log n) or O(1)Binary search, math
What to say in the interview: "The brute force is O(n²) because of the nested loop. With n up to 10⁵ that's too slow, so I'll use a hashmap to get O(n) time at the cost of O(n) space." That one sentence shows everything they grade.

Avoid these

Common mistakes

  • Calling a loop with x in some_list inside it O(n). It's O(n²).
  • Saying O(n²) when two different lists are nested. It's O(a · b).
  • Forgetting the call stack when giving space complexity for recursion.
  • Saying O(n) for a sort-based solution. Sorting alone is O(n log n).
  • Only giving time complexity. Always give time and space.
  • Mixing up average and worst case for hashmaps. Say "O(1) average" if asked to be precise.
