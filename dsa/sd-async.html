The idea

A restaurant's order rail

A waiter takes your order and clips the ticket to a rail. They don't stand in the kitchen waiting for your food; they go serve other tables. Cooks pull tickets in order at their own pace. That rail is a message queue: the waiter (your web server) replies fast, the cooks (workers) do the slow part, and a rush of orders just makes the rail longer instead of making the waiter freeze.

Synchronous (call and wait)Asynchronous (queue)
Real lifeA phone callA text message or email
User waits forThe whole jobOnly "accepted"
If the worker is downRequest failsJobs wait in the queue
Use forReads, anything the user needs nowEmails, video processing, notifications, analytics

Pagination: offset vs cursor

Offset pagination is "start reading at page 50." If someone inserts pages at the front while you read, you see repeats. Cursor pagination is a bookmark: "continue after this exact post," which stays correct while new posts arrive.

Use cursor pagination for feeds and anything that changes often: the cursor encodes the last item seen (e.g. its timestamp + ID), and the query is WHERE id < cursor ORDER BY id DESC LIMIT 20, which uses an index instead of skipping rows.

Communication patterns

Six ways services talk

1. Message queue (point to point)

Each job handled once

A deli's "take a number" machine. Each customer number is called once, by whichever clerk is free next.

Use forbackground jobs: sending emails, resizing images, transcoding video. Add workers to go faster. Examples: Google Cloud Pub/Sub (with one subscription), Amazon SQS, RabbitMQ.

2. Pub/sub (publish–subscribe)

One event, many listeners

A newspaper is printed once and delivered to every subscriber. The paper doesn't know or care who reads it.

Use whenone event triggers several independent reactions. "Order placed" → payment service charges, warehouse packs, email service confirms, analytics counts. The order service doesn't call each one; it publishes one event.

3. Event log (Kafka-style stream)

Replayable history

A ship's logbook: entries are appended in order and never erased. Anyone can read from any page, and a new crew member can read the whole book from the start to catch up.

Use forhigh-volume streams (clicks, metrics, location updates), and when new consumers must replay history. Messages stay for days; each consumer tracks its own position (offset). Partitions keep order per key.

4. Polling, long polling, SSE, WebSockets

Getting updates to clients

Waiting for a package: checking the porch every 5 minutes (polling), asking the courier to call when they're on your street (long polling), a one-way radio update stream (server-sent events), or an open phone line where both of you can talk any time (WebSocket).

MethodDirectionUse for
Short pollingClient asks repeatedlyRare updates; simplest

5. Idempotency

Safe to retry

Pressing an elevator button five times still calls the elevator once. Pressing "Pay" twice must also charge only once.

Whyqueues and retries mean a message can arrive twice. Make handlers idempotent: the client sends a unique idempotency key with the request; the server stores processed keys and returns the saved result for duplicates.

def charge(request):
    key = request.headers["Idempotency-Key"]
    saved = db.get_result(key)
    if saved: return saved                 # duplicate: don't charge again
    result = payments.charge(request.amount)
    db.save_result(key, result)              # ideally in the same transaction
    return result
Delivery guaranteeMeaningNeeds
At most onceMay lose messages, never duplicatesFine for metrics you can drop
At least onceNever loses, may duplicateThe common default; pair with idempotent handlers
Exactly onceEach effect happens onceHard; in practice "at least once + idempotency"

6. Rate limiting

Protect the system from floods

A nightclub bouncer letting in a few people each minute. A group of friends can come in together if the room has space, but a crowd of 500 can't all rush in at once.

Useto stop abuse, scrapers and accidental retry storms, and to share capacity fairly between customers. Reply 429 Too Many Requests with a Retry-After header.

AlgorithmIdeaTrade-off
Token bucketTokens refill at a steady rate; each request spends oneAllows short bursts; the common choice

Deep analysis

Video upload: sync where it matters, async everywhere else

Dropping off film at a photo lab. The counter gives you a ticket right away; developing, printing and enlarging happen in the back; you get a text when it's ready.

Client asks the API for an upload URL (synchronous, fast). The server returns a signed URL for object storage.

Client uploads the file straight to object storage, in resumable chunks. Your app servers never touch the gigabytes.

Storage publishes "upload finished" to a pub/sub topic.

Subscribers react in parallel: a transcoding queue creates 240p–4K versions; a thumbnail worker; a content-safety scanner; a search indexer.

When transcoding completes, status flips to "ready" and a notification goes to the uploader. Failed jobs retry; jobs that keep failing go to a dead-letter queue for a human to inspect.

Say which steps are synchronous and which are async, and why. "The user only waits for the upload; transcoding happens through a queue so spikes don't affect the site" is exactly the reasoning interviewers listen for.
