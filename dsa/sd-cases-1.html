Walkthrough 1 · Beginner

Design a URL shortener (like bit.ly)

A coat check: you hand over a long coat (the long URL) and get a small ticket (the short code). Anyone with the ticket gets the coat back instantly. The hard part is printing billions of unique tickets and finding coats fast.

1. Requirements

  • Functional: create a short URL from a long one (optional custom alias, optional expiry); redirect short → long.
  • Non-functional: redirects in < 50 ms, very high availability (broken links are bad), codes not guessable in sequence, links never lost.

2. Estimates

  • 100 M new URLs/month ≈ 40 writes/s. Reads 100× more ≈ 4,000 redirects/s (~10,000 at peak).
  • Storage: 100 M × 12 months × 5 years × 500 bytes ≈ 3 TB. Small enough for a few database nodes.
  • Codes needed: 6 billion over 5 years. 62⁷ ≈ 3.5 trillion, so 7 characters is plenty.

3. API

POST /v1/urls  {"long_url": "https://...", "alias": "optional", "expires_at": null}
     → 201 {"short_url": "https://sho.rt/2TX"}
GET  /{code}   → 301 or 302 Location: https://...   (404 if unknown or expired)

4. Data model

urls: code (PK, 7 chars) | long_url | user_id | created_at | expires_at

5. High-level design

client ──▶ LB ──▶ API servers ──▶ cache (code → long_url, ~90%+ hits)
                     │                     │ miss
                     ├── ID generator ──┐  ▼
                     └─────────────────▶ key-value DB (sharded by code)

6. Deep dive: generating the code

OptionHowTrade-off
Hash the URL (MD5) and take 7 charsSame URL → same codeCollisions need checking and retrying
Counter + base-62Unique number → codeNo collisions; sequential codes are guessable unless you shuffle/encrypt the number
Pre-generated key serviceBatch of unused random codes handed to each serverFast, unguessable; must track used keys

A good answer: a distributed ID generator (each server reserves a range of 1,000 numbers at a time from a coordinator, so no per-request coordination), shuffle the bits so codes aren't sequential, then base-62 encode.

7. Other decisions

  • 301 vs 302: 301 (permanent) lets browsers cache the redirect, which cuts load but hides clicks from analytics. 302 keeps every click visible.
  • Analytics: publish a click event to a queue; never slow the redirect for it.
  • Abuse: rate-limit creation per user, scan long URLs against malware lists.
  • Expiry: check on read, and clean up with a background job.
Walkthrough 2 · Intermediate

Design a distributed rate limiter

A theme park ride with a ticket scanner at each of several gates. Each family has a limit of 5 rides per hour, and all gates must share one count, otherwise a family could go through each gate separately and ride 5 times per gate.

1. Requirements

  • Limit requests per key (user ID, API key or IP) per time window, with different rules per endpoint ("100 posts/hour," "10 logins/minute").
  • Adds less than ~1–2 ms per request; works across many API servers; if the limiter itself fails, let traffic through (fail open) rather than take down the site.
  • Return 429 with Retry-After and remaining-quota headers.

2. Where it runs

In the API gateway or as middleware on every API server, with counters in a shared Redis cluster so all servers see one count.

client ─▶ API gateway ─(check key)─▶ Redis cluster (counters, sharded by key)
               │ allowed                       ▲
               ▼                               │ rules cached locally,
          backend services            rules DB ┘ refreshed every minute

3. Algorithm

Token bucket per key, stored as (tokens, last_refill_time). On each request, compute refill since last time, subtract one if available. Do the read-modify-write atomically in Redis (a Lua script) so two servers can't both spend the last token.

4. Deep dives

  • Hot keys: one abusive client hammering one Redis shard. Add a small local limiter per server as a first filter.
  • Latency: Redis in the same data center (~0.5 ms). For extreme scale, each server can take a batch of tokens locally and sync periodically, trading precision for speed.
  • Multi-region: per-region limits, or approximate global counts synced asynchronously.
  • Failure: if Redis is unreachable, fail open with a conservative local limit and alert.
Walkthrough 3 · Advanced (very Google)

Design a web crawler

A librarian tasked with cataloguing every book in every library in the world. Each book's bibliography points to more books. They keep a to-visit list, never visit the same book twice, don't overwhelm any single library with visits, and skip libraries that say "no visitors."

1. Requirements

  • Start from seed URLs; download pages; extract links; repeat. Store pages for indexing.
  • Scale: 1 billion pages/month ≈ 400 pages/s. At 500 KB each ≈ 500 TB/month of raw HTML.
  • Be polite (obey robots.txt, limit requests per site), avoid duplicates, handle traps (infinite calendars), and keep pages fresh.

2. High-level design

seed URLs ─▶ URL frontier (priority + per-host queues)
                 │
                 ▼
        fetcher workers ──(DNS cache, robots.txt cache)──▶ the web
                 │ HTML
                 ▼
        content store (object storage) ──▶ dedup (content fingerprint)
                 │
                 ▼
        link extractor ──▶ URL filter + "seen URLs" set ──▶ back to frontier

3. Deep dives

URL frontier: front queues by priority (PageRank, how often the page changes) and back queues per host, each host handled by one worker with a delay between requests. That's how politeness is enforced.

Seen-URL check at billions of URLs: a Bloom filter in memory answers "definitely new" or "probably seen" using a few bits per URL, backed by a disk store for certainty.

Duplicate content: many URLs serve the same page. Store a fingerprint (hash or SimHash for near-duplicates) of each page and skip repeats.

Traps and junk: cap URL length and depth per site, normalize URLs (lowercase host, strip tracking parameters), blacklist known traps.

Scale out: partition by hostname (consistent hashing), so each worker owns a set of hosts; this also keeps politeness local to one machine.

Freshness: re-crawl news sites hourly and static pages monthly, based on how often each page has changed before.

This is Google's origin story, so interviewers may push on politeness, dedup and prioritization. Mention BFS over the link graph, a Bloom filter for seen URLs, and per-host queues, and you've covered the core.
