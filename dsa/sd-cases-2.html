How to read these

Same recipe, different dishes

A chef who knows how to make a sauce, braise and roast can cook almost any menu. These three designs reuse the same building blocks (cache, queue, shard, replicate) in different combinations. Notice which block solves which problem, because that's what transfers to a design you've never seen.

Walkthrough 4 · Intermediate

Design a news feed (like Instagram or X)

A mail room in an apartment building. When someone sends a flyer, the mail room can put a copy in every resident's mailbox right away (push), or residents can come to the lobby and read the bulletin board when they want (pull). Pushing is great for small flyers; for a flyer to 100 million residents, a bulletin board is the only sane option.

1. Requirements

  • Users post (text, photos); follow others; see a feed of followed users' posts, newest or ranked first, paginated.
  • 200 M DAU, feed loads in < 200 ms; a new post can take a few seconds to appear (eventual consistency is fine).

2. Estimates

  • Feed reads: 200 M × 10 opens/day = 2 B/day ≈ 20,000/s. Posts: 200 M × 0.5 = 100 M/day ≈ 1,000/s.
  • Average 200 followers → 1,000 posts/s × 200 = 200,000 feed inserts/s if we push to everyone.

3. Data model

users(user_id, name, ...)                      -- SQL
follows(follower_id, followee_id)              -- sharded by follower_id (and an index by followee)
posts(post_id, author_id, text, media_url, created_at)   -- sharded by author_id
feed_cache: user_id → [post_id, post_id, ...]  -- Redis list, newest 500

4. High-level design

post:  client ─▶ API ─▶ posts DB ─▶ queue ─▶ fan-out workers ─▶ followers' feed caches
read:  client ─▶ API ─▶ feed cache (post IDs) ─▶ post cache / DB (hydrate) ─▶ ranked page
media: client ─▶ object storage ─▶ CDN

5. Deep dive: fan-out

Fan-out on write (push)Fan-out on read (pull)
Post costHigh: one insert per followerLow: one insert
Read costLow: one cache readHigh: query every followee and merge
Problem caseCelebrities (millions of followers)Users following thousands of accounts

Hybrid answer: push for normal authors; for accounts above ~10,000 followers, skip the push and merge their recent posts in at read time. Skip pushing to inactive users too; build their feed when they return.

6. Other decisions

  • Ranking: fetch a few hundred candidates, score them (recency, closeness, engagement) in a ranking service, return the top 20.
  • Pagination: cursor-based on (score or time, post_id).
  • Counts (likes): sharded counters with write-back caching; approximate is fine.
Walkthrough 5 · Intermediate

Design a chat app (like WhatsApp or Google Chat)

A switchboard operator with a phone line open to everyone who's awake. When Ana says something for Bob, the operator says it straight down Bob's line. If Bob's phone is off, the operator writes it in Bob's message book and reads it to him when he wakes up.

1. Requirements

  • 1:1 and group chats (up to ~500 members); delivered/read receipts; online status; message history on all devices; push notifications when offline.
  • 500 M DAU × 40 messages ≈ 20 B/day ≈ 230,000 messages/s. Delivery under ~200 ms; messages must never be lost and must keep order within a chat.

2. High-level design

Ana ══ WebSocket ══ chat server 7 ─┐
                                   ├─▶ message store (wide-column, partition = chat_id)
Bob ══ WebSocket ══ chat server 3 ◀┤
                                   ├─▶ presence/session store (Redis: user → server)
                                   └─▶ push notification service (if Bob is offline)

3. Sending a message, step by step

Ana's app sends the message over her open WebSocket, with a client-generated ID (for idempotency on retry).

Chat server 7 assigns a server timestamp/sequence, stores it in the message store, and acks Ana (one grey tick: sent).

It looks up Bob in the session store: he's connected to server 3. It forwards the message there (directly or via pub/sub).

Server 3 pushes it down Bob's WebSocket; Bob's app acks (two ticks: delivered). Opening the chat sends a read receipt.

If Bob is offline, the message waits in storage and a push notification is sent. When Bob reconnects, his app asks "everything after the last message ID I have," per chat.

4. Deep dives

  • Millions of connections: each chat server holds ~50,000–100,000 WebSockets; ~10 M concurrent users means a few hundred servers. A load balancer assigns connections; the session store tracks who's where.
  • Ordering: a per-chat sequence number assigned by one owner of that chat (or the partition leader), not by client clocks.
  • Groups: fan out to each online member's server; for big groups, have members pull history.
  • Presence: heartbeats every ~30 s; mark offline after missed heartbeats; publish status changes only to friends who are online.
  • End-to-end encryption: servers store ciphertext they can't read; keys live on devices.
Walkthrough 6 · Advanced (very Google)

Design search autocomplete (typeahead)

A librarian who has memorized the 10 most-asked book titles for every possible first few letters. As you say "har…", they instantly reply "Harry Potter, Harvard Business Review, Harper Lee…" without searching the shelves, because they prepared those lists last night.

1. Requirements

  • As the user types, show the top 10 completions by popularity. Must feel instant: < 100 ms including network.
  • Billions of queries/day; each keystroke is a request, so ~5× the search volume: hundreds of thousands of requests/s.
  • Suggestions can lag reality by minutes to hours; trending topics should appear within ~an hour.

2. Core data structure

A trie of past queries, where each node stores its precomputed top 10 completions. A lookup is just "walk to the prefix's node, return its list": O(length of prefix), no searching subtrees at request time.

          (root)
           │ g
          [g] top: google, gmail, google maps, ...
           │ o
          [go] top: google, google maps, good morning, ...
           │ o
          [goo] top: google, google maps, google translate, ...

3. High-level design

read path:   browser (debounce, cache) ─▶ CDN/edge ─▶ suggestion servers (trie shards in RAM)
build path:  search logs ─▶ aggregation job (counts per query, time-decayed)
                         ─▶ trie builder ─▶ new trie snapshot ─▶ swapped into servers

4. Deep dives

  • Build offline, serve read-only: a batch job (MapReduce-style) recomputes counts and tries every hour or so; servers load the new snapshot and swap atomically. A small streaming layer can boost fast-trending queries.
  • Sharding: by prefix range (a–c, d–f…) adjusted for uneven letter popularity, with replicas of each shard for load and failover.
  • Client tricks: wait ~100 ms after the last keystroke (debounce), cache results in the browser ("goo" results are reusable while typing "goog"), and cancel outdated requests.
  • Personalization and safety: blend in the user's own history; filter offensive or harmful suggestions before they reach the trie.
  • Languages: separate tries per language/region.

Interviewers want the key insight: precompute top-k at every trie node so serving is a lookup, and rebuild offline from logs. Then show you can shard it and keep it fast with client-side debouncing and caching.
