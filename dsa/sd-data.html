System design

Databases and data at scale

The database is usually the hardest part to scale, because it holds the truth. This page covers choosing SQL vs NoSQL, indexes, replication, sharding, consistent hashing, and the CAP trade-off.

The idea

A library that keeps growing

A town library starts with one librarian and a card catalog (an index). As readers multiply, it photocopies popular books into reading rooms (replicas). When the building is full, it opens branches: A–M in one building, N–Z in another (shards). Each step makes the library bigger and faster, and each makes some things harder: the copies can be out of date, and a question about "all books" now means visiting every branch.

Choosing

SQL vs NoSQL

A filing cabinet with labeled forms where every form has the same boxes (SQL) versus a set of folders where each folder can hold whatever papers it needs (document NoSQL). Forms make cross-checking easy; folders make it easy to add new kinds of information.

TypeExamplesShapeGreat for
Relational (SQL)PostgreSQL, MySQL, Cloud SpannerTables, fixed schema, joinsMoney, orders, users, anything needing transactions
Key-valueRedis, DynamoDBkey → valueSessions, caches, carts, very high throughput

Default answer: start with SQL unless you have a reason not to. Choose NoSQL when you need massive write scale, simple access by key, flexible schema, or easy horizontal scaling, and you can live without joins and multi-row transactions. Big files never go in a database; store them in object storage and keep the URL in the database.

Techniques

Six techniques for data at scale

1. Indexes

O(log n) lookups instead of O(n) scans

The index at the back of a textbook. Without it, finding "photosynthesis" means reading every page. With it, you jump to page 142. But every time the book gains a page, the index has to be updated too.

Useon columns you filter, join or sort by. Most databases use a B-tree, which keeps keys sorted so range queries are fast. Each index speeds reads but slows writes and uses space.

CREATE INDEX idx_posts_user_time ON posts (user_id, created_at DESC);
-- now fast: a user's newest posts
SELECT * FROM posts WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;

2. Transactions and ACID

All or nothing

A bank transfer: take $100 from Alice and give it to Bob. If the power cuts out halfway, money must not vanish or be created. Either both steps happen or neither does.

  • Atomic: all steps or none.
  • Consistent: rules (like "balance ≥ 0") always hold.
  • Isolated: concurrent transactions don't see each other's half-done work.
  • Durable: once committed, it survives crashes.

3. Replication

More reads, survive failures

A teacher writes the homework on the main board, and student helpers copy it onto boards in other rooms. Students anywhere can read it, but a helper who's slow to copy shows yesterday's homework for a few minutes.

Leader–follower: writes go to the leader, which copies changes to followers; reads can go to followers. Scales reads and gives failover. Multi-leader / leaderless: writes accepted in several places (good across regions), but conflicts must be resolved.

Synchronous replication waits for followers before confirming a write (safe, slower). Asynchronous confirms right away (fast, may lose the last writes if the leader dies).

4. Sharding (partitioning)

Scale writes and storage

A phone book too big for one volume is split into A–F, G–M, N–S, T–Z. Each volume is smaller and can sit on a different shelf. Finding "Patel" means opening only one volume. Listing everyone in a city means opening all four.

Use whenone machine can't hold the data or handle the writes. Each shard is a separate database holding part of the rows.

Shard key strategyHowWatch out for
Rangeuser_id 1–1M on shard 1, 1M–2M on shard 2…Hot spots (new users all land on the last shard)
Hashhash(user_id) decides the shardRange queries hit every shard
DirectoryA lookup table maps key → shardThe table is extra infrastructure
GeoUsers stored in their regionUneven region sizes

Pick a shard key that matches your most common query (for chat: conversation_id, so one conversation's messages live together) and spreads load evenly. Cross-shard joins and transactions become slow or impossible, so design around them.

5. Consistent hashing

Add or remove nodes, move few keys

Mail carriers around a circular road, each covering the houses from their own post clockwise to the next carrier. Hiring one new carrier only changes the route of the carrier just ahead of them; everyone else keeps their houses.

Usefor distributing keys across cache or database nodes when nodes come and go. With hash % N, changing N moves almost every key.

6. Denormalization

Faster reads, duplicated data

Writing a friend's phone number in both your phone and your address book. Looking it up is faster wherever you are, but when they change number, you have to update both places.

Usewhen joins are too slow or impossible across shards: store the author's name inside each post, or keep a precomputed follower count instead of counting rows each time.

Theory you'll be asked about

CAP theorem and consistency models

Two bank branches lose their phone line between them. A customer wants to withdraw money. Branch A can refuse until the line is back (consistent, not available), or allow it and risk the account being overdrawn at Branch B too (available, not consistent). It can't guarantee both while the line is down.

CAP: when a network Partition happens, a distributed system must choose Consistency (every read sees the latest write, or gets an error) or Availability (every request gets an answer, maybe stale). Partitions do happen, so the real choice is C or A during them.

ChooseExample systemsUse for
CP (consistent)Spanner, ZooKeeper, a single-leader SQL DBPayments, inventory, bookings, unique usernames
AP (available)Cassandra, DynamoDB (default), DNSLikes, feeds, view counts, shopping cart adds

PACELC adds: else, when the network is fine, you still trade Latency for Consistency (waiting for replicas to agree takes time).

Deep analysis

Designing storage for a chat app's messages

A post office that stores letters by conversation instead of by date: each pair of pen pals has one box, and new letters go on top. Reading the latest 50 letters in any conversation means opening one box.

Access pattern: "load the latest 50 messages of conversation X," then scroll back. Writes: 1 B messages/day ≈ 10,000/s average.

Volume: 1 B × 200 bytes ≈ 200 GB/day, ~70 TB/year. Too much for one SQL machine.

Choice: a wide-column store (Bigtable/Cassandra). Partition key = conversation_id (all of one chat together), clustering key = message_id sorted newest first.

IDs: time-sortable unique IDs (Snowflake-style) so sorting by ID is sorting by time. See Reliability.

Elsewhere: user accounts and contacts stay in SQL (small, relational); photos go to object storage with URLs in the message.

Google built Bigtable, Spanner and Colossus, so interviewers like hearing why you'd pick a wide-column store vs a globally consistent SQL database. Justify the choice from the access pattern, not the brand name.
