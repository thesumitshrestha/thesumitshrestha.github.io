System design

Distributed systems and reliability

Once a system runs on thousands of machines, something is always broken. Advanced design is about expecting failure: timeouts, retries, circuit breakers, quorums, consensus, unique IDs, distributed transactions, and monitoring that tells you what went wrong.

The idea

Planning a group trip by text message

Ten friends plan a trip over group chat. Some messages arrive late, some phones die, and two people book different hotels because they didn't see each other's message. Nobody can be sure everyone has read the latest plan. Distributed systems have exactly these problems: messages are slow or lost, machines crash, clocks disagree, and there's no single moment when everyone knows the same thing.

The fallacies of distributed computing

Beginners assume these are true. All of them are false:

  • The network is reliable, and latency is zero.
  • Bandwidth is infinite, and the network is secure.
  • Nothing changes (topology), and there's one administrator.
  • Transport cost is zero, and the network is uniform.
Techniques

Eight techniques for staying up

1. Timeouts

Never wait forever

If a friend doesn't reply to "dinner at 7?" by 6:30, you make other plans. Without a deadline you'd sit there all night.

Ruleevery network call gets a timeout, set from the dependency's normal p99 latency. A slow dependency without timeouts ties up all your threads and takes you down with it.

2. Retries with exponential backoff and jitter

Retry politely

Calling a busy restaurant: try again in 1 minute, then 2, then 4. If 1,000 people all redial at exactly the same second, the line stays jammed, so everyone waits a slightly random extra amount.

Use fortemporary errors (timeouts, 503). Only retry idempotent operations, cap the attempts, and add randomness so clients don't retry in sync (a "retry storm").

import random, time
def call_with_retry(fn, attempts=5, base=0.1, cap=5.0):
    for i in range(attempts):
        try:
            return fn()
        except TransientError:
            if i == attempts - 1: raise
            time.sleep(random.uniform(0, min(cap, base * 2 ** i)))   # full jitter

3. Circuit breaker

Fail fast, let it recover

The breaker in your home's fuse box cuts power when something shorts, so the wires don't catch fire. You reset it once the fault is fixed.

Usearound calls to dependencies that can fail. After repeated failures, stop calling for a while and return a fallback, giving the dependency room to recover.

Related: bulkheads (separate thread pools per dependency, like watertight compartments in a ship) and graceful degradation (show the feed without recommendations rather than an error page).

4. Quorums (N, R, W)

Tunable consistency

A club with 5 board members. A decision needs 3 signatures (W = 3), and to check the latest decision you ask any 3 members (R = 3). Since 3 + 3 > 5, at least one person you ask signed the latest decision.

Rulewith N replicas, a write waits for W acknowledgements and a read asks R replicas. If R + W > N, every read overlaps the latest write. Common: N = 3, W = 2, R = 2. Lower W or R for speed at the cost of consistency.

5. Leader election and consensus

Agreeing despite failures

A class electing a class president. Once a majority votes for someone, that's the president, even if a few students were absent. If the president leaves, a new vote happens. Two presidents at once would be chaos, so you always need a majority.

Usewhen nodes must agree on one value: who's the leader, the order of log entries, a configuration. Raft and Paxos do this with a majority of nodes (so 5 nodes tolerate 2 failures). In practice you use a system built on them (etcd, ZooKeeper, Chubby at Google, Spanner) rather than writing your own.

6. Unique ID generation

IDs without a central counter

Tickets at a deli with many counters. Instead of everyone sharing one ticket machine, each counter prints "counter number + time + its own count," so numbers never clash and still roughly sort by time.

Optionsa database auto-increment (simple, a bottleneck at scale); UUIDs (no coordination, 128 bits, not sortable); Snowflake-style 64-bit IDs = timestamp + machine ID + per-millisecond sequence (sortable by time, no coordination).

7. Distributed transactions: 2PC and sagas

Changes across services

Booking a trip with a flight, hotel and car. Two-phase commit is a travel agent who asks all three "can you hold it?" and only says "book it" if all agree. A saga books each one in turn, and if the car rental fails, it cancels the hotel and flight (compensating actions).

2PCgives atomicity but blocks if the coordinator dies, and is slow across services. Sagas are the usual microservice answer: a sequence of local transactions, each with an undo step. Pair with the outbox pattern (write the event into the same database transaction, publish it afterwards) so events are never lost.

8. Observability

Know what's broken before users tell you

A car dashboard: the speedometer and fuel gauge (metrics), the trip computer's history (logs), and a mechanic's diagnostic trace of exactly which part misfired (traces).

SignalAnswersExample
MetricsIs something wrong?Error rate, p99 latency, QPS, CPU
LogsWhat happened in this event?"payment 81 failed: card declined"
TracesWhere did the time go across services?Request spent 400 ms waiting on the recommendation service

Google's SRE practice: define SLIs (what you measure, e.g. % of requests under 300 ms), SLOs (the target, e.g. 99.9%), and an error budget (the 0.1% you're allowed to fail, which you can "spend" on risky launches). Alert on symptoms users feel, not on every CPU blip.

Deep analysis

A cascading failure, and how each technique stops it

One stalled car on a highway causes a jam that spreads miles back, blocking on-ramps and side streets that had nothing to do with the original problem.

Trigger: the recommendations service slows from 50 ms to 5 s after a bad deploy.

Spread: the feed service waits on it with no timeout. Its threads fill up, so even requests that don't need recommendations queue up. Fix: timeouts.

Amplify: clients see errors and retry immediately, tripling traffic. Fix: backoff with jitter, retry budgets.

Collapse: the overloaded recommendations service can never recover because traffic never stops. Fix: circuit breaker, load shedding (reject low-priority requests early).

Better outcome: the breaker opens, the feed shows posts without recommendations (graceful degradation), alerts fire on the SLO, and the deploy is rolled back.

For L4, you don't need to explain Paxos. You do need to say "timeouts, retries with backoff, idempotency, replication, and monitoring" naturally whenever you add a network call to your design.
