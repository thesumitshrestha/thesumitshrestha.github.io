System design

Scaling: from one server to millions of users

Scaling means handling more users without getting slower or falling over. The core moves are: make servers stateless, add more of them behind a load balancer, push static content to a CDN, and remove every single point of failure.

The idea

A bigger oven or more ovens

A bakery that can't keep up has two options. Buy a bigger oven (vertical scaling): easy, but ovens only get so big, and if that one oven breaks, there's no bread. Or buy more ovens (horizontal scaling): almost no upper limit, and one broken oven just means slightly slower service, but now you need someone to split orders between ovens and every baker must follow the same recipe card.

The journey

Growing an app step by step

A lemonade stand becoming a chain: first one stand, then a separate storeroom, then more sellers, then a cooler of pre-made cups, then branches in other towns. Each step fixes the bottleneck the previous step created.

1 server, ~100 users. Web app and database on one machine. Simple and fine.

Split the database out, ~1,000s of users. App and DB stop fighting for CPU and memory; each can be sized separately.

Load balancer + several app servers, ~100,000s. Requires stateless servers (sessions move to a cache or database).

Cache + read replicas. The database becomes the bottleneck; take reads off it.

CDN for static files. Images and video stop hitting your servers at all.

Queues for slow work. Emails, video processing, notifications run in the background.

Shard the database, millions+. Split data across many database machines.

Multiple regions. Copies of the system on several continents for speed and disaster recovery.

Building blocks

Six building blocks for scale

1. Stateless servers

Prerequisite for scaling out

A bank where any teller can help you because your account lives in the bank's central system, not in one teller's notebook. If tellers kept private notebooks, you'd have to queue for the same teller every time, and if they went home sick, your records would be gone.

Meansno user data lives in a server's memory between requests. Sessions, carts and uploads go to a shared store (Redis, a database, object storage).

Stateful (bad for scale)         Stateless (good)
user → server 2 (has cart)       user → any server → shared Redis (has cart)
server 2 dies → cart lost        any server dies → nothing lost

2. Load balancer

Spreads traffic, hides failures

A restaurant host who seats each new party at the next free table and stops seating people at a table whose waiter has gone home.

Doesdistributes requests, runs health checks, removes dead servers, terminates TLS (HTTPS), and gives clients one address to call.

AlgorithmHow it picksGood when
Round robinEach server in turnServers and requests are similar
Weighted round robinBigger servers get more turnsMixed machine sizes
Least connectionsServer with fewest active requestsRequests vary in length (uploads, websockets)
IP / consistent hashSame client → same serverYou need stickiness or cache locality

Layer 4 balancers route by IP and port only (very fast). Layer 7 balancers read the HTTP request, so they can route /api/video and /api/chat to different services. The balancer itself is run as a redundant pair so it isn't a single point of failure.

3. CDN (content delivery network)

Static content near users

A soft-drink company doesn't ship every can from one factory to each buyer; it stocks corner shops in every neighborhood. A CDN stocks copies of your images, videos and scripts in hundreds of cities.

Use forimages, video, CSS/JS, downloads, and even cacheable API responses. Cuts latency from ~150 ms to ~10–20 ms and removes most traffic from your servers.

  • Pull CDN: on the first request in a city, the CDN fetches from your server and caches it. Simple; first user is slower.
  • Push CDN: you upload files to the CDN ahead of time. Good for big, predictable content like a new movie.
  • Invalidate by changing the file name (app.v42.js) rather than waiting for a timeout.

4. Reverse proxy and API gateway

One front door

A hotel front desk. Guests don't wander to the kitchen or laundry directly; the desk checks who they are, answers simple questions, and sends requests to the right department.

Doesauthentication, rate limiting, routing to the right microservice, request logging, compression, and TLS, so each service doesn't reimplement them.

5. Autoscaling

Capacity that follows demand

A supermarket opening more checkout lanes when queues get long on Saturday, and closing them at night so cashiers aren't paid to stand around.

Doesadds servers when CPU or request rate passes a threshold, removes them when traffic falls. Needs stateless servers and fast startup. Keep a minimum count for sudden spikes, since new machines take a minute or more to boot.

6. Removing single points of failure

Redundancy at every layer

A plane has two engines, two pilots, and backup hydraulics. Any one part can fail and the plane still lands.

Checkevery box in your diagram and ask "what if this dies?" Then add: two load balancers, many app servers, database replicas with automatic failover, multiple availability zones (separate buildings), and eventually multiple regions.

Deep analysis

Sizing a service: how many servers?

Hiring staff for a concert: 20,000 fans arriving in one hour at the gates, each ticket check taking 10 seconds, tells you how many gates to open, plus a few extra in case of a jammed scanner.

Traffic: 50 M DAU × 20 requests/day = 1 B/day ÷ 10⁵ ≈ 10,000 requests/s average, ~30,000/s at peak.

Per-server capacity: measure, don't guess. Say one server handles 1,000 requests/s at safe CPU (~60%).

Servers: 30,000 ÷ 1,000 = 30 for peak. Add headroom for a zone failure (N+1 or +50%): about 45 servers across 3 zones.

Bottleneck check: 30,000 req/s each doing 2 database queries = 60,000 queries/s. One database can't do that, so cache (90% hit rate → 6,000 queries/s) and add read replicas.

The pattern interviewers want: estimate load → find the first component that breaks → add the cheapest fix (cache, replica, queue, shard) → repeat for the next bottleneck.

Avoid these

Common scaling mistakes

Widening one lane of a highway doesn't help if the bridge ahead is still one lane. Scaling the part that isn't the bottleneck changes nothing.

  • Adding app servers when the database is the real bottleneck.
  • Sticky sessions that quietly make servers stateful again.
  • One load balancer, one database, one region: all single points of failure.
  • Scaling before measuring. Profile first; often one slow query is the whole problem.
  • Forgetting that autoscaling takes minutes; sudden spikes need headroom or a queue.
